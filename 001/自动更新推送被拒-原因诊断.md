### 3.2 一次运行的「暴露窗口」= 从检出到推送的整段时长

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 正文说明 | 日报作业实测 1 分 52 秒 ~ 2 分 12 秒（数据齐时），上限 `timeout-minutes: 15`； 市场数据库作业上限 20 分钟。按平均 51 分钟一次的外部推动、单次窗口 2 分钟粗算， **每次运行约 4% 概率撞上**；这段时间里日报两条流水线一共跑了约 34 次， 实际被拒 3 次（≈9%，10-03~10-04 正好是 PR 合并最密集的两天，与模型一致）。 |
| 02 | 窗口还会被放大 | `schedule` 触发在 GitHub 平台负载高时**本身就会延迟排队**， 定时档与手动档撞车的概率随之上升（②号就是这么来的）。 |

### 3.3 而三个工作流当时的防护是这样的

| 工作流 | 并发锁 | 推送被拒后的处理 |
|---|---|---|
| `octopus-daily.yml` | ❌ 无 | ❌ 无 —— 直接失败 |
| `manual.yml` | ❌ 无 | ❌ 无 —— 直接失败 |
| `market-db.yml` | ✅ `market-db` | ⚠️ 一次性 `git pull --rebase --autostash origin HEAD` 后重推 |

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 正文说明 | `market-db.yml` 那个一次性补救也有两个毛病（这次一并换掉）： |
| 02 | 要点说明 | **只重试一次**，且 rebase 一旦撞车（两边都改了同一个文件）就把作业留在**半截 rebase 状态**里， 第二次 push 也失败，本次落库内容彻底丢失； |
| 03 | 要点说明 | `git pull … origin HEAD` 里的 `HEAD` 指的是**远端的默认分支**，靠「默认分支恰好就是要推的分支」 这个隐含前提成立，换个触发分支就会 rebase 到错误的基线上。 |

### 3.4 顺带查出来的一个**静默丢数据**缺陷（比推送被拒更隐蔽）

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 正文说明 | `manual.yml` 的提交清单只有 4 个文件： |
| 02 | 代码/命令 L1 (`text`) | `git add output/daily_report_*.html output/latest.html \` |
| 03 | 代码/命令 L2 (`text`) | `output/sentiment_history.json output/news_history.json` |
| 04 | 正文说明 | 而 `output/pipeline.py` 每跑一轮还会写 **`quant_history.json`**（量化分析总览留痕与结算）、 **`hk7_forecast.json`**（AI 七日港股走势留痕）、**`weekly_forecast.json`**（每周量化走势留痕）—— `octopus-daily.yml` 的注释里特意强调过这三个「必须一起提交，否则预测留痕 / 命中率每次都会从零开始」。 |
| 05 | 也就是说 | **手动跑的那一轮，这三个留痕从来就没进过库**（推送成功也没进）。 下一轮定时任务会在「旧状态」上重新结算，所以通常表现为**留痕晚一轮**； 但如果某天只有手动运行、没有定时运行（或手动运行是当天第一次发出预测）， **这一天的留痕就是彻底没有**，命中率统计相应少一条样本。已一并修掉。 |

## 五、修复方案

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 原则 | **先把「不该并发的」串起来，再让「无法避免的并发」可恢复**。 |
| 02 | 口径与适用范围 | 以上内容按结构化多行多列表格呈现，供核对与查阅 |

### 5.1 新增 `tools/safe_push.sh` —— 被拒后把本次改动**重放**到远端最新提交之上

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 代码/命令 L1 (`text`) | `暂存 pathspec → 无新内容就跳过 → 提交 → push` |
| 02 | 代码/命令 L2 (`text`) | `└─ 被拒（且确认是「远端前进」类型）` |
| 03 | 代码/命令 L3 (`text`) | `→ git fetch 远端分支` |
| 04 | 代码/命令 L4 (`text`) | `→ git reset --hard <远端 tip>` |
| 05 | 代码/命令 L5 (`text`) | `→ 逐个文件重放本次提交的改动（按 5.2 的规则裁决）` |
| 06 | 代码/命令 L6 (`text`) | `→ 重新提交（同一条提交信息）→ 再 push` |
| 07 | 代码/命令 L7 (`text`) | `（最多 --attempts 次，默认 5；线性退避 + 随机抖动，避免两个 runner 打乒乓）` |
| 08 | 正文说明 | 四个刻意的设计选择： |
| 09 | 要点说明 | **不用 `git rebase` / `git pull --rebase`**：rebase 撞车会把作业留在半截状态， 还要解析冲突标记、处理「提交变空」等分支。重放是**确定性**的： 先站到远端 tip 上，再把「本次提交动过的那几个文件」按规则贴回去， 永远不会有冲突标记，也不会残留 rebase 状态（已用回归钉死）。 |
| 10 | **只碰本次提交动过的文件** | 远端对 README / 代码 / 文档的改动一律保留， **绝不因为日报作业把别人刚合并的 PR 回退掉**（这是「重放」而不是「强推」的关键区别）。 |
| 11 | **不是「远端前进」类的失败立即失败** | 权限不足、保护分支、钩子拒绝（`GH006`） 这些重试 5 次也不会好，只会浪费 5 分钟并淹没真实原因 —— 直接红，并把 git 原始输出打出来。 |
| 12 | 要点说明 | **重放后若发现远端已含相同内容**（重跑同一轮很常见）：不产生重复提交， `Everything up-to-date` 也算成功。 |

### 5.2 新增 `tools/merge_generated.py` —— 重放时的文件级裁决规则

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 正文说明 | 两边都改过同一个文件时，**按文件性质**裁决，而不是一刀切「取本次」： |
| 02 | 口径与适用范围 | 以上内容按结构化多行多列表格呈现，供核对与查阅 |

| 文件 | 策略 | 理由 |
|---|---|---|
| `output/daily_report_*.html`、`output/latest.html` | **整份取本次** | 每轮都是整份重新生成，本次是更晚完成的一轮，数据更新 |
| `output/news_history.json` | **并集**（键 = 日期 + 标题） | 追加型标题存档；两边各自抓到了对方没有的标题。远端已确认的**中国政府网官方溯源不被媒体同名记录降级**（与 `pipeline._merge_news_corpus` 同口径） |
| `output/sentiment_history.json` | **并集**（键 = 个股 → 日期） | 情绪跨日基线；同一天以本次为准，远端独有的个股 / 日期全部保留 |
| `output/quant_history.json` | **并集**（键 = 日期，逐层递归） | 量化留痕；本次优先，但**本次的空值不擦掉远端已结算的 `result`** |
| `output/hk7_forecast.json`、`output/weekly_forecast.json` | **并集**（键 = 标的 + 锚定日），按 `issued_cst` 稳定排序 | 预测留痕；**已结算（`settled=true`）的历史事实不被未结算副本覆盖**；排序是因为这些文件按「尾部 N 条」裁剪，顺序错了会裁掉新条目 |
| `output/market_db/*.json` | **整份取本次** + 告警 | 文件自带 `integrity.hash`（sha256 自校验），**任何内容级合并都会让哈希对不上**，反而破坏自检；同日三档本来就由本作业顺序累加，且有 `market-db` 并发锁兜底 |
| 其它 `.json` | 递归合并（本次优先、远端补空） | 未来新增的状态文件默认不丢数据 |
| README / 代码 / 文档等**非生成物** | **一律保留远端** | 日报作业无权改别人的东西 |

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 正文说明 | 输出格式与各写入方**逐字一致**（`pipeline._atomic_write` 用 `indent=1`； |
| 02 | 补充说明 | `hk_seven_day` / `octopus_weekly` / `octopus_quant.engine` 用 compact + `sort_keys=True`； |
| 03 | 补充说明 | 结尾换行按原文件保留）—— 否则合并一次就会造成整文件无意义 diff，之后每轮都脏。 |
| 04 | 补充说明 | 已用「仓库里真实留痕文件的逐字节往返」回归钉死。 |

### 5.3 三个工作流统一接线 + 日报两条共用一把锁

| 改动 | 文件 | 说明 |
|---|---|---|
| 提交推送改调 `tools/safe_push.sh` | `octopus-daily.yml`、`manual.yml`、`market-db.yml` | 三处逻辑一致，不再各写一份（也不会再漂移） |
| 新增 `concurrency: {group: octopus-report, cancel-in-progress: false}` | `octopus-daily.yml`、`manual.yml` | 两个作业生成同一批文件、推同一分支，**排队而不取消**（取消会打断「已推微信、还没提交留痕」的那一轮）。②号事故从根上不会再发生 |
| 手动作业补齐 3 个留痕 JSON | `manual.yml` | 与定时作业提交同一批文件（见 3.4） |
| 新增「🧯 推送失败兜底」Artifact 步骤 | `octopus-daily.yml`、`manual.yml` | 万一 5 次重放都失败（远端持续在动 / 权限问题），把这轮日报与留痕存成 Artifact 保留 14 天，可人工补提交，不再「白跑一轮」 |
| `market-db.yml` 保留自己的锁 | `market-db.yml` | **不与日报共用**：它单轮可长达 20 分钟，共用会把 09:00 的微信推送堵在后面。它与日报的文件集完全不相交，重放必然干净 |

## 七、剩余风险与可选后续

| 项 | 说明 |
|---|---|
| 极端连撞 | 5 次重放内远端一直在动 → 放弃并标红（生成物已存 Artifact）。按当前 main 的推动频率（51 分钟一次）几乎不可能，真发生了也应人工看一眼是谁在刷提交 |
| 排队等待 | 手动触发若撞上定时作业在跑，会在 `octopus-report` 锁上排队（最长一个作业时长，定时作业上限 15 分钟）。GitHub 同一把锁只保留最新一个排队作业，连点多次只会保留最后一次 —— 这是刻意的：并行跑同一批文件只会互相踩 |
| 微信已推送但提交失败 | 仍可能出现（推送在提交之前）。此时页面已收到日报、库里少一轮留痕，Artifact 里有完整生成物可人工补提交 |
| 可选：留痕按轮次分文件 | 把 `hk7_forecast.json` 之类改成「每轮一个小文件 + 读取时聚合」，可让同文件竞争彻底消失（现在靠并集合并已经够安全，属于长期优化） |
| 可选：给 main 配保护规则 | 若之后给 bot 提交加保护规则，记得放行 `octopus-bot`，否则会命中 5.1 第 3 条「立即失败」路径（这是期望行为：会直接告诉你原因，而不是空转重试） |
| 可选：给 PR 加一条离线回归工作流 | 本仓库现在的 Actions 只跑日报、**不校验 PR**（781 项回归全靠人工 / 会话里跑）。加一条 `pull_request` 触发的 `python3 -m unittest discover -s tests` 只需 2~3 分钟、全程离线不推送，本次新增的 43 项也就能自动拦住「工作流清单漏了留痕文件」这类漂移 |
