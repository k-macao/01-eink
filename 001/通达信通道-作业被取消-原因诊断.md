# 🐙 诊断报告：市场数据库定时任务为什么「被取消」——通达信通道把作业拖到超时

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 2026-10-01 · 排查对象 | `.github/workflows/market-db.yml`（运行模式：采集 → 交叉验证 → 自检 → 写库）、`output/market_db.py` 第 ⑥ 路源「通达信行情 mootdx」 结论先行：**不是配置没写对，也不是 GitHub 挂了**。 |
| 02 | 补充说明 | 日志里那三行 `mootdx` 提示只是**噪音**； |
| 03 | 补充说明 | 真凶是**单台死主站**——`tdxpy` 的 `connect()` 把 `socket.timeout` 吞掉并 `return False`，`mootdx` 又不检查返回值，死站于是被当成「连上了」，之后每次 API 调用都要跑一遍 `auto_retry` 阶梯（4 次重连 × 5s + 退避 sleep）。 |
| 04 | 补充说明 | 11 只沪深标的 ≈ 34 次调用 × 每次几秒 = **单站约 6 分钟**，主站池最多 4 台 → **约 24 分钟 > 作业 20 分钟上限** → 被取消（`Error: The operation was canceled.`）。 |
| 05 | 补充说明 | 被 kill 时 Python 的 stdout 缓冲整段丢失，只剩 `mootdx` 的 stderr 三行，于是看上去像「配置文件问题」。 |

## 二、逐条对上证据

### 2.1 那三行 = `mootdx` 首次使用的「自动选路」路径（噪音，但暴露了真实缺陷）

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 正文说明 | `mootdx.quotes.StdQuotes.__init__` 一定会先调 `mootdx.config.setup()`；配置文件不存在时它会调 `bestip()` 现场探测 38+ 个主站。我们的 `collect()` 用 `ThreadPoolExecutor` **并行跑 6 路源**， 所以 `setup()` 是在 worker 线程里执行的，而 `mootdx.server.server()` 里写的是 `asyncio.get_event_loop()` —— 在非主线程、且没有运行中的事件循环时直接抛 `RuntimeError`， 被 `bestip()` 的 `except RuntimeError` 接住，打的就是这句 `请手动运行 python -m mootdx bestip`。 随后它仍然 `json.dump` 了一份配置，`BESTIP` 是空串。 |
| 02 | 正文说明 | 本地复现（同一份代码 + 一个「能连上但不回数据」的黑洞主站 + 假 HOME）： |
| 03 | 代码/命令 L1 (`text`) | `2026-10-01 15:19:53,015 - mootdx - WARNING - 未找到配置文件 /tmp/repro/home/.mootdx/config.json, 正在生成配置文件.` |
| 04 | 代码/命令 L2 (`text`) | `2026-10-01 15:19:53,015 - mootdx - INFO - [-] 选择最快的服务器...` |
| 05 | 代码/命令 L3 (`text`) | `2026-10-01 15:19:53,015 - mootdx - ERROR - 请手动运行`python -m mootdx bestip`` |
| 06 | **逐字对上**。所以 | 这三行只是「配置首次生成 + 线程里选路失败」，它本身不慢（2ms）； 但它说明**每次 CI 都要把 mootdx 的配置重建一遍**，且建出来的配置是没用的空 `BESTIP`。 |

### 2.2 stdout 为什么整段消失

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 正文说明 | `python3 output/market_db.py pull` 的进度全走 `print`（stdout），GC 模式下 stdout 是**块缓冲**： 进程被 kill 时缓冲区不会 flush，**整段进度日志蒸发**。 |
| 02 | 补充说明 | 而 `mootdx` 走 `logging`（stderr，无缓冲）， 所以日志尾部只剩那三行 —— 这就是「看起来像配置问题」的视觉陷阱。 |

### 2.3 真凶：死主站的「静默失败 → 重连阶梯」

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 正文说明 | `tdxpy/base_socket_client.py`： |

| 05 | 代码/命令 L4 (`python`) | `...` |
| 06 | 代码/命令 L5 (`python`) | `return False` — ← 吞掉异常，只返回 False |

| 08 | 代码/命令 L1 (`python`) | `if self.auto_retry and self.client:` |

| 11 | 代码/命令 L4 (`python`) | `self.disconnect()` |

### 2.4 为什么定时任务平时没事、这次爆

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | 要点说明 | 平时主站池前几台能连上，很快命中； |
| 02 | 要点说明 | 一旦前几台被丢包（跨境网络抖动 / 主站维护 / 出口策略变化），就会走进上面的阶梯； |
| 03 | 20 | 00 档（`1700`）还要额外抓 22 次 `finance` / `xdxr`，是最容易踩线的档位。 |

## 三、修复（四道闸，全部落在 `output/market_db.py`）

| 闸 | 代码位置 | 做法 |
|---|---|---|
| ① 预置配置 | `_tdx_config_payload` / `_ensure_tdx_config` / `_mootdx_config_path` | 建客户端**之前**按 mootdx 自己的格式写好 `$HOME/.mootdx/config.json`（`SERVER` 主机池 + `BESTIP`＝本次要连的主站）；已有配置原样尊重；写不进去静默降级。路径可用 `OCTOPUS_DB_TDX_CONFIG` 覆盖 |
| ② TCP 预检 | `_tdx_probe` | 先用自己的 socket 探一次（`TDX_PROBE_TIMEOUT`=3s），连不上的站**不交给 mootdx** —— 直接从源头掐掉「静默失败 → 重连阶梯」 |
| ③ 先验活后明细 | `_tdx_from_client` | 改成**先 `quotes()` 一次拿全标的**（既是数据也是验活），行情为空立刻换站；只有验活通过才做逐只 `bars`/`finance`/`xdxr`。客户端显式 `auto_retry=False`，重试责任交给「主站池逐个降级」。行情时间戳仍由日K交易日回填（`_tdx_restamp`），口径不变 |
| ④ 总预算 | `_tdx_deadline` / `_tdx_time_left` / `fetch_tdx` | 整条通道 `TDX_BUDGET_SEC`=90s（`OCTOPUS_DB_TDX_BUDGET` 可覆盖）；逐站、逐只调用前都看表，到点收工并如实写失败原因（如 `总预算 90s 用尽，停止试连（已试 1 台）`） |

## 五、以后怎么避免同类问题

| 序号 | 维度 / 条目 | 详细内容与说明 |
|---:|---|---|
| 01 | **第三方库的「静默失败」必须自己验活** | `connect()` 返回 `False` / `None` 不能当作成功； 凡是在线程池里跑的采集源，都要有「一次调用验活 + 总预算」。 |
| 02 | **CI 里 stdout 一律 `PYTHONUNBUFFERED=1`** | 被取消的作业才有完整日志，否则排查全靠猜。 |
| 03 | **单源必须有墙钟预算** | 并行采集时，`collect()` 会等最慢的一路；只要有一路无上限， 整个作业就没有上限。 |
| 04 | **作业超时值要和「最慢单源」对账** | 本次 24 分钟 vs 20 分钟，差一点点就是「看起来随机失败」。 |
